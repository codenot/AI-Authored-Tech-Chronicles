默认熟悉 RTP 媒体传输、编码码率与播放缓冲。本文统一网络观测口径，串联算法、反馈协议和媒体执行链，最后按时间回顾主要算法家族。示例采用可复算的合成数据，工程实现以固定版本的标准与 WebRTC 源码为锚点。

一、延迟与带宽：先统一测量口径

流媒体系统的拥塞控制同时约束交付速率、排队时间和媒体有效期限。传输层交付成功不等于帧仍有播放价值；码率达到目标也不等于链路没有积压。分析之前，需要把端到端延迟和网络控制器实际可观察的量分开。

1.1 延迟、RTT 与 jitter 分别描述什么

指标定义与使用常见误读
单向网络时延从实际发包到接收；跨端绝对时间相减需要时钟同步或偏移校准直接用接收时间 − 发送时间，忽略两端时钟偏移
RTT一次往返测量；具体是否扣除反馈等待取决于协议和测量点RTT / 2 就是当前去程时延
排队时延链路或端点缓冲中的等待；可观测本地 pacer 队列，网络内部通常需估计RTT − minRTT 精确等于去程队列
jitter包间传输时延的变化；RTP RR 的 interarrival jitter 为平滑后的统计量jitter 数值就是 jitter buffer 当前长度
媒体端到端延迟采集到呈现，包含网络之外的处理与缓冲网络 RTT 良好就能排除编码、组帧和渲染积压

在路径稳定时，较低 RTT 可以用作传播与端点开销的近似基线；但反向拥塞、路由切换和处理延迟都会改变差值。判断网络积压还应联合到达趋势、实际交付速率与本地队列。RTP 的时间戳是媒体时钟，不能直接拿来替代网络发送时间。

1.2 容量、可用带宽、吞吐量与 goodput

术语工程含义控制器需要注意
路径容量 capacity路径瓶颈在给定口径下可提供的服务速率 C多跳、无线调度和速率限制器使 C 随时间变化
可用带宽 available bandwidth扣除竞争流量后，特定时间尺度内剩余的服务能力剩余量与本流实际能竞争到的公平份额并不完全相同
交付吞吐量 delivery rate观测窗口内实际到达或被确认的字节 / 时间应用受限、ACK 压缩和窗口选择会影响样本
媒体有效吞吐 goodput去除重复、修复等开销后的有效媒体交付到达但赶不上解码时限的帧仍可能没有业务价值
编码码率 / 线上码率编码器输出与实际网络发送分别计量RTP/UDP/IP、RTX、FEC、padding、探测流量都可能占预算

1.3 BDP、inflight 与队列：速率之外还有存量

固定服务速率的近似模型BDP = BtlBw × RTpropdQ / dt = R − C（Q > 0；空队列处不继续减小）queue_delay ≈ Q / C

速率用 bit/s，时间用 s，BDP 与 Q 用 bit。inflight 指已发出但尚未被确认的数据；它包含路径在途数据，不能全部视为排队。

例如 1 Mbps × 60 ms = 60 kbit = 7.5 kB。理想模型中，这些数据足以维持管道工作；在相同服务速率下额外堆积 30 kB，会增加约 240 ms 的等待。即便发送速率已经等于出口速率，既有队列也可以保持不变。控制器因此既要考虑速率，也要考虑在途量及队列状态。

媒体应用还可能在低运动场景中产生不足流量，进入 application-limited 状态。此时低接收速率说明样本供给不足，不能据此把路径容量直接下调。上述媒体时限要求可对照 RFC8836。

二、BBR：用带宽与传播时延建立路径模型

BBR 的基本思路是估计瓶颈带宽 BtlBw与往返传播时延 RTprop，据此控制 pacing rate 和在途量。它不必等到缓冲溢出才获得容量线索：交付速率提供服务能力样本，较低 RTT 提供路径时延基线。两个估计都带有观测窗口和样本有效性条件。

概念模型；具体增益与上限取决于版本和状态pacing_rate ≈ pacing_gain × estimated_BtlBwinflight_target ≈ cwnd_gain × estimated_BtlBw × estimated_RTprop

不能同时把带宽峰值和 RTT 最小值视为随时可读的真值。模型需要通过探测获得新样本，也需要防止受限发送与聚合反馈污染估计。

Startup 解决冷启动时缺少容量估计的问题；Drain 补偿探测期间产生的积压；ProbeBW 在利用链路与寻找新容量之间切换；ProbeRTT 尝试避免 RTT 基线被持续排队长期抬高。原始设计可见 2016 年 BBR 论文。

版本边界：BBRv1、v2、v3 不能只用同一组固定 gain 概括。后续版本引入或调整带宽、在途量的边界以及对丢包、ECN 的响应，改善过度探测与共存问题。本文模型说明参考 BBR 工作草案 -06，版本入口见 Google BBR 项目；工作草案并非已发布 RFC。

工程取舍：BBR 需要探测才能发现容量提升，探测可能制造短时队列。最小 RTT 会受到路由变化影响，交付速率也可能受 ACK 聚合影响；模型与竞争流的交互需按版本和网络条件验证。BBR 本身不理解视频帧依赖或播放截止时间，接入媒体栈仍需码率分配和过期数据策略。

三、GCC：从到达时序推断拥塞趋势

GCC（Google Congestion Control）把媒体发送速率适配与实时传输结合。延迟分支的核心输入是相邻包组的发送间隔与到达间隔之差；交付速率、丢包、探测结果等共同参与最终速率决策。它控制的是预算与发送行为，反馈数据可由接收端通过 RTCP 返回。

发送时间 s 与到达时间 a，各自在本端时钟下取差分Δdᵢ = (aᵢ − aᵢ₋₁) − (sᵢ − sᵢ₋₁)accumulated_delayᵢ = accumulated_delayᵢ₋₁ + Δdᵢ

固定时钟偏移被消去，频率误差仍然存在。包组聚合、乱序处理与突发过滤会影响进入估计器的有效样本。

3.1 不能把历史 Kalman 模型等同于当前实现

2016 年 GCC 草案 -02 描述了包括 Kalman 到达滤波器在内的历史设计。本文读取的 WebRTC 源码中，TrendlineEstimator 的路径是：累积延迟变化，经指数平滑，在窗口内拟合斜率，再结合阈值与持续性判断过载。

GoogCcNetworkController 还连接 acknowledged bitrate、delay-based BWE、loss-based BWE、probe controller 与约束处理。DelayBasedBwe 是其中一个分支。这里固定到源码提交 0d3c711211f7；具体产品还取决于其依赖版本与 field trial 配置。

四、RTCP 与 TWCC：反馈协议如何支撑估计器

RTCP 是控制报文体系，TWCC 是一套传输范围的包级反馈机制，GCC 是控制算法。三者处在不同层次。传统 SR/RR 给出周期性会话与接收统计；拥塞控制需要更细的包级到达信息时，可以协商相应 RTP 扩展和 RTCP 反馈格式。

机制携带的信息不承担的职责
RTCP SR / RRSR 的 NTP/RTP 时间映射；报告块的 fraction lost、累计丢失、最高序号、jitter、LSR/DLSR 等不直接给出完整逐包到达时间或可用带宽真值
NACK / PLI请求包重传或图像恢复的反馈不是网络容量估计，也不免除修复流量预算
REMB接收端估计的最大接收码率及相关 SSRC不是到达时序明细；估计逻辑更多留在接收端
TWCCtransport-wide 序号对应的接收状态与到达时间差不决定降速幅度，也不完成媒体预算分配
GCC / BBR使用反馈与发送状态，计算控制目标不能替代反馈编码与媒体执行模块

SR/RR 字段及 jitter 定义见 RFC3550；基于反馈的 RTP/AVPF 框架见 RFC4585。LSR/DLSR 可用于 SR/RR 往返测量并扣除接收端报告等待，但仍不提供单向路径的精确分解。

4.1 解码后的时间比“反馈包到了”更重要

反馈包包含覆盖范围、接收状态与压缩后的到达时间差，发送端重建接收时间序列，并查找对应的本地发送记录。丢失发送历史、序号回绕处理错误，或把 RTCP 报文到达时间当成媒体包到达时间，都会污染估计器输入。乱序包和暂未到达的包也应按反馈语义与后续信息处理。

4.2 TWCC 与 RFC 8888 CCFB 是不同线格式

常见 TWCC 反馈采用 RTPFB / PT=205 / FMT=15，源于 transport-wide CC 草案的格式与字段定义。该历史草案正文存在 PT 表述不一致，应以格式图与字段定义结合实现核对。RFC 8888 的 CCFB 使用 RTPFB / PT=205 / FMT=11，按 SSRC 与 RTP 序号反馈，不能当成 TWCC 同一个格式的更名版本。

排障时需核对 SDP 中协商的 extmap、rtcp-fb、双方实际支持的反馈格式及统计口径。反馈频率本身也有成本：周期过长会扩大控制滞后，过密则增加反向开销，反向队列还可能进一步延缓决策。

五、完整示例：从逐包反馈到码率与队列变化

用一条上行视频流演示测量 → 反馈 → 判断 → 决策 → 执行 → 再测量。下列时间与报文均为合成数据，叙述采用统一参考时轴；实际端点时钟不必同步，估计器使用各自时间差。这组数据用于复算控制环路，实际 GCC 状态需从实现日志确认。

t=0 时瓶颈服务能力降至 1 Mbps；发送维持 4 Mbps，队列初始为空，无竞争流与丢包。

5.1 包间隔被拉长，反馈揭示持续的正延迟变化

5.2 RTCP 返回的是到达记录，发送端完成推断

接收端在 t=90 ms 形成反馈，覆盖 base_seq=1000、status_count=6，六包状态均为 received。解码后的到达时间为 [40, 50, 60, 70, 80, 90] ms。这是逻辑字段展示：实际 TWCC 用 reference time、状态 chunks 与 recv deltas 压缩编码；完整 RTCP 头、填充和量化需由协议实现处理。

若总网络预算为 800 kbps，一种明确的分配示例是：音频 64 kbps、视频 656 kbps、协议与修复预留 80 kbps。计费口径必须与控制器一致。pacer 可能为了排空本地队列暂时采用不同于媒体目标的速率；不能把它的配置机械地等同于编码码率。

5.3 降速已经生效，网络积压仍然存在

按流体近似，t=120 ms 时积压为 (4 − 1) Mbps × 0.12 s = 360 kbit = 45 kB，对应 360 ms 队列等待。随后总发送立即变为 0.8 Mbps，净排空速度只有 0.2 Mbps，因此需 1.8 s 才能排空。离散包模型存在约一个服务包的粒度差异；编码器与 pacer 响应滞后则可能继续增加峰值。

如果帧已经无法赶上播放时限，降低未来码率不能挽救在网络中的旧数据。本地可按媒体依赖关系丢弃尚未发送的过期数据，必要时请求恢复帧；正在网络队列里的包通常无法由发送端撤回。RTX 与 FEC 也必须计入负载，并结合剩余时限使用，见 RFC4588。

5.4 用脚本复算观测与队列，和实现日志对齐

# 可复算的合成记录；长度按示例瓶颈服务的字节口径计量。
packets = [
    # transport 序号, 发送 ms, 到达 ms, 字节数
    (1000,  0.0, 40.0, 1250),
    (1001,  2.5, 50.0, 1250),
    (1002,  5.0, 60.0, 1250),
    (1003,  7.5, 70.0, 1250),
    (1004, 10.0, 80.0, 1250),
    (1005, 12.5, 90.0, 1250),
]
# 相邻差分消去固定时钟偏移；没有在此实现 GCC 的分组或滤波。
delay_deltas = [
    (cur[2] - prev[2]) - (cur[1] - prev[1])
    for prev, cur in zip(packets, packets[1:])
]
# 用首包到末包的时间跨度，仅计随后五个包，避免窗口边界多算一个包。
span_s = (packets[-1][2] - packets[0][2]) / 1000
rate_bps = sum(p[3] for p in packets[1:]) * 8 / span_s
# 以下为流体队列模型；0.8 Mbps 是显式选定的演示目标，不是 GCC 输出。
send_bps, capacity_bps, target_bps = 4e6, 1e6, 0.8e6
feedback_time_s = 0.120
queue_bits = (send_bps - capacity_bps) * feedback_time_s
drain_s = queue_bits / (capacity_bps - target_bps)
print(f"delay deltas (ms): {delay_deltas}")
print(f"delivery rate: {rate_bps / 1e6:.2f} Mbps")
print(f"queue at feedback: {queue_bits / 8 / 1000:.1f} kB")
print(f"drain time after reduction: {drain_s:.2f} s")

脚本验证的是字节与时间口径、差分信号及排空时间，没有实现 BBR 或 GCC。复现到实际系统时，应同时记录发包历史、反馈覆盖范围、估计器状态、target bitrate、实际编码输出、pacer 队列与帧丢弃。只有最后两项恢复，才说明控制目标已经落实到媒体流水线；单独观察 target bitrate 曲线不够。

六、拥塞控制算法演进：TCP 与 UDP 两条主线

按传输栈回顾算法，更容易看清反馈从哪里来、控制逻辑在哪里执行，以及如何影响媒体。TCP 由传输层提供可靠传输与拥塞控制；UDP 本身没有拥塞控制，需由上层协议或应用补齐。以下分别回顾 TCP 和 UDP 上层的主要算法与代表实现，年份仍区分论文、技术报告与 RFC 节点。

6.1 TCP 主线：从丢包驱动的窗口调整到路径建模

TCP 的 ACK 既确认交付，也提供反馈时钟。控制器根据丢包、RTT、交付速率或 ECN 更新拥塞窗口与发送节奏；实际发送还受到接收窗口和应用供给约束。应用写入 socket 的速度不等于线上发送速度，TCP send buffer 也可能成为媒体延迟的一部分。

这条线的关键问题依次是：防止拥塞崩溃、改善丢包恢复、提高高 BDP 链路利用率、提前感知排队、减少对丢包触发的依赖。这些方向并存，而非简单的新算法替代旧算法；例如 NewReno 主要改进恢复流程，BBR 则改变路径估计与控制方法。

对流媒体的影响：TCP 可以保障有序可靠的字节流，但丢失数据的恢复可能推迟后续字节交付。直播与点播可通过播放缓冲吸收部分变化；交互媒体还需约束应用队列、媒体产生量和数据时限。拥塞窗口变小后继续以原速率写入，只会把积压转移到发送端。

6.2 UDP 主线：由上层建立反馈与发送控制

UDP 只提供数据报承载，应用不能因缺少 TCP 窗口就持续无约束发送。RFC 8085要求使用 UDP 的应用或上层协议采用适当的拥塞控制机制。这里的“UDP 算法”指部署在 UDP 之上的控制器，并非 UDP 协议内部新增了算法。

实时媒体的路线从平滑速率与 TCP 友好性，发展到包级反馈、排队趋势与媒体队列协同。TFRC 提供模型化速率控制；GCC、SCReAM、NADA 更直接针对实时媒体。LEDBAT 面向低优先级背景传输；PCC、Vivace、Copa 是通用研究路线，在 UDP 用户态传输等实现中探索新的控制方法，并不等同于 RTP 专用算法。

对 RTP 实时媒体的影响：控制器需要把反馈结果落实到音视频预算、编码输出、pacer 和修复开销，同时处理已经过期的媒体。SCReAM 也使用窗口与自时钟机制，因此不能把 TCP/UDP 的区别简化为“窗口算法 / 纯码率算法”。媒体栈通常拥有更多丢弃与修复策略的选择，也承担更多协调职责。

跨协议的连接点：QUIC 与 BBR

QUIC 运行于 UDP 之上，自行提供 ACK、丢失恢复和拥塞控制。RFC 9002 第 7 节给出类似 NewReno 的控制方案，并允许选择其他算法；BBR 项目同时提供 TCP 与 QUIC 实现入口。因此 BBR 在 TCP 时间线中回顾其版本演进，在 UDP 场景中仍可能使用，不能将其归为 TCP 专属。

6.4 回到流媒体系统：沿各自传输栈检查完整环路

回顾一个方案时，依次检查观测量是否可靠、决策如何处理噪声与滞后、执行端是否跟上、过期媒体是否退出队列。相同 target bitrate 下，编码输出、探测开销、pacer 积压和帧丢弃不同，用户看到的卡顿与延迟就可能完全不同。针对专业流媒体系统，容量阶跃、竞争流、无线突发、反向反馈拥塞与帧截止时间应一起纳入验证。
