# AdaptiveJitterBuffer 设计文档

## 一、概述

AdaptiveJitterBuffer 是自适应抖动缓冲与音视频同步系统的核心模块，提供：
- 自适应缓冲深度（根据网络抖动动态调整）
- 变速播放能力（加速追赶/减速积累/跳帧）
- 音视频同步控制

---

## 二、核心设计理念

### 2.1 驱动模式：设备拉取模式

**类比 WebRTC NetEq**：

```
mixlib（类似 Audio Device Module）
    ↓ 定时 onTick 请求数据
AdaptiveJitterBuffer.TryOutputFrames()
    ↓ 被动响应
返回结果：
    - 音频：必须返回数据（有 PLC）
    - 视频：可返回 false（等待/黑帧）
```

**关键点**：
- jitter buffer **不主动推送**，被动响应请求
- jitter buffer **不决定何时输出**，由 mixlib 定时驱动
- jitter buffer 只决定**输出什么**（帧、PLC帧、false）
- **音频 PLC 在 jitter buffer 内部实现**（重复最后一帧）
- **视频不做 PLC**，返回 false 由 mixlib 处理

## 四、核心组件详解

### 4.1 JitterEstimator（抖动估计器）

**职责**：计算网络抖动统计量

**输入**：
- RTP timestamp
- 到达时间 arrival_ms

**计算公式**：
```
理想到达间隔 = (rtp_ts差值) × 1000 / clock_rate
实际到达间隔 = arrival_ms差值
抖动值 = 实际间隔 - 理想间隔
```

**输出**：
```cpp
struct JitterStats {
    float mean_ms;           // 平均抖动
    float variance_ms;       // 抖动方差（稳定性指标）
    float max_deviation_ms;  // 最大偏差
    float percentile95_ms;   // 95 分位数（覆盖95%情况）
    JitterTrend trend;       // 趋势：kStable/kIncreasing/kDecreasing
};
```

**时间戳回绕处理**：
- 使用 int64_t 处理 32 位 RTP timestamp 回绕
- 差值 > 2^31 → 正向回绕（减去 2^32）
- 差值 < -2^31 → 负向回绕（加上 2^32）

---

### 4.2 TargetDelayCalculator（目标延迟计算器）

**职责**：根据抖动统计计算目标缓冲延迟

**核心公式**（WebRTC NetEq 思想）：
```
// 抖动延迟
jitter_delay = base_delay + jitter_factor × sqrt(variance)

// 最终目标延迟（取最大值，非相加！）
target_delay = max(jitter_delay, minimum_delay, sync_delay)
```

**参数配置**：
| 参数 | 默认值 | 说明 |
|------|--------|------|
| base_delay_ms | 30 | 最小基准延迟 |
| jitter_factor | 3.0 | 抖动补偿系数（3σ 覆盖 99.7%） |
| max_delay_ms | 400 | 最大允许延迟 |
| min_delay_ms | 20 | 最小延迟 |
| max_step_ms | 10 | 单次最大变化步长 |
| trend_expand_ms | 20 | 趋势增大时预扩大 |

**sync_delay 传递方式**（WebRTC 方式）：
```cpp
// 通过 SetMinimumDelay 接口传入
void SetMinimumDelay(uint32_t delay_ms);
minimum_delay_ = delay_ms;

// 计算时取 max
target_delay = std::max(jitter_delay, minimum_delay_);
```

**平滑更新**：每次最多变化 ±10ms，避免突变

---

### 4.3 BufferDepthController（缓冲深度控制器）

**职责**：根据缓冲深度和目标延迟决策播放策略

**状态判定**：
| 状态 | 条件（buffer_depth/target_delay） | play_rate | 行为 |
|------|-----------------------------------|-----------|------|
| kUnderflow | < 30% | 1.3 | 最大加速，跳帧追赶 |
| kLow | 30%-50% | 1.0~1.3 | 加速追赶 |
| kNormal | 50%-150% | 1.0 | 正常播放 |
| kHigh | 150%-200% | 0.85~1.0 | 正常输出（mixlib 消耗慢自然减速） |
| kOverflow | > 200% | 0.85 | 跳帧 |

**输出**：
```cpp
struct PlayoutDecision {
    BufferState state;              // 当前缓冲状态
    float play_rate;                // 播放速率建议
    uint32_t frames_to_skip;        // 需跳过的帧数
    bool skip_non_key_frames;       // 只跳非关键帧
    bool need_key_frame;            // 是否请求关键帧
};
```

---

### 4.4 VideoFrameAssembler（视频帧组装器）

**职责**：将 RTP 包组装成完整的视频帧

**支持的编解码**：
- H264：单 NAL、STAP-A、FU-A
- H265：单 NAL、AP、FU

**输出**：
```cpp
struct VideoFrame {
    std::string buffer;       // NAL 数据（组帧后的完整帧）
    bool is_key_frame;        // 是否关键帧
    bool is_complete;         // 是否完整（marker 到达）
    int64_t rtp_timestamp;    // RTP 时间戳（展开后）
    uint16_t start_seq;       // 帧起始序列号
    uint16_t end_seq;         // 帧结束序列号
    uint64_t arrival_ms;      // 最后包到达时间
    uint32_t clock_rate;      // 时钟频率（90000）
};
```

---

### 4.5 SharedTimeBaseManager（共同时间线管理器）

**职责**：管理音视频流的 RTP-NTP 时间映射

**核心功能**：
- RegisterStream(stream_id, clock_rate)：注册流
- UpdateTimeBase(stream_id, ntp_ms, rtp_ts)：从 RTCP SR 更新
- CompareStreams(video_id, audio_id, video_rtp, audio_rtp)：比较音视频偏差

**时间转换公式**：
```
本地时间 = ntp_ms + (rtp_ts - base_rtp_ts) × 1000 / clock_rate
```

---

### 4.6 AudioVideoSyncController（音视频同步控制器）

**职责**：计算音视频同步调整决策

**运行模式**：
| 模式 | 条件 | 行为 |
|------|------|------|
| kVideoOnly | 只有视频有效 | 无同步决策 |
| kAudioOnly | 只有音频有效 | 无同步决策 |
| kAudioVideoSync | 音视频都有效 | 计算同步决策 |

**同步状态**：
| 状态 | A/V 偏差范围 | 处理 |
|------|-------------|------|
| kInSync | < 50ms | 无需调整 |
| kAudioLeading | 50-200ms | 音频减速 / 视频加速 |
| kVideoLeading | 50-200ms | 视频减速 / 音频加速 |
| kSevereDesync | > 200ms | 强制对齐（跳帧） |

**输出**：
```cpp
struct SyncDecision {
    SyncMode mode;                  // 运行模式
    SyncState state;                // 同步状态
    int64_t av_offset_ms;           // 音视频偏差（video - audio）
    float video_rate_adjust;        // 视频速率调整
    float audio_rate_adjust;        // 音频速率调整
    bool video_skip_frames;         // 是否跳视频帧
    uint32_t video_frames_to_skip;  // 跳帧数
    bool force_align;               // 强制对齐标志
    bool sync_priority;             // 同步是否优先于抖动决策
};
```

## 五、关键算法

### 5.1 buffer_depth_ms 计算

**正确方式**：使用 RTP timestamp 计算实际数据时长

```cpp
uint32_t CalculateBufferDepth() {
    uint32_t oldest_rtp = oldest_packet->GetTimestamp();
    uint32_t newest_rtp = newest_packet->GetTimestamp();
    
    // 处理时间戳回绕
    int64_t rtp_diff = newest_rtp - oldest_rtp;
    if (rtp_diff < 0) rtp_diff += 0x100000000LL;
    
    // 转换成毫秒
    return rtp_diff * 1000 / clock_rate;
}
```

**错误方式（已修复）**：使用到达时间差（受网络延迟影响）

---

### 5.2 CanOutputFrame() 判断

**与 BufferDepthController 状态一致**：

```cpp
bool CanOutputFrame() {
    if (packet_queue_.empty()) return false;
    if (waiting_key_frame_) return false;
    
    PlayoutDecision decision = GetPlayoutDecision();
    
    // 欠载且需要关键帧 → 等待
    if (decision.state == kUnderflow && decision.need_key_frame) {
        return false;
    }
    
    // 其他状态都输出（变速在 AssembleAndOutput 内部处理）
    return true;
}
```

**WebRTC 方式**（正确）：
```cpp
// sync_delay 通过 SetMinimumDelay 传入
// target_delay = max(jitter_delay, sync_delay)
target_delay = std::max(base_target_level, minimum_delay);

    if (sync_decision.mode == kAudioVideoSync) {
        if (sync_decision.sync_priority) {

## 六、变速机制落地

### 6.1 加速（play_rate > 1.0）

**实现方式**：在 AssembleAndOutput 内部跳帧

```
play_rate = 1.2 → 跳过 20% 的非关键帧
输出给 mixlib 的帧少了 → 自然加速消耗
```

### 6.2 减速（play_rate < 1.0）

**实现方式**：正常输出帧

```
play_rate = 0.9 → 正常输出
mixlib 消耗慢 → 缓冲自然积累
```

### 6.3 OVERFLOW（缓冲过多）

**实现方式**：直接跳帧

```
frames_to_skip = 3 → 跳过 3 帧非关键帧
减少缓冲堆积
```

    uint32_t ssrc = packet->GetSsrc();
    
    if (ssrc == video_stream_id) {
        video_jitter_buffer.ReceivePacket(packet);
    } else if (ssrc == audio_stream_id) {
        audio_jitter_buffer.ReceivePacket(packet);
    }

### 7.3 RTCP SR 更新

```cpp

    time_base_manager.UpdateTimeBase(ssrc, ntp_ms, rtp_ts);
}
```

### 7.4 定时输出（mixlib onTick）

```cpp
void OnTick() {
    // 从 jitter buffer 取帧
    std::vector<VideoFrame> video_frames;
    while (video_jitter_buffer.TryOutputFrames(video_frames)) {
        for (auto& frame : video_frames) {
            // 输出到 mixlib
        }
        video_frames.clear();
    }
}
```

### 7.5 同步计算（定时执行）

```cpp
void OnSyncTimer() {
    // 1. 计算音视频同步偏差
    int64_t av_offset_ms = CalculateAVOffset(
        time_base_manager,
        video_stream_id, audio_stream_id,
        video_jitter_buffer.GetCurrentRtpTimestamp(),
        audio_jitter_buffer.GetCurrentRtpTimestamp());
    
    // 2. 计算 sync_delay（WebRTC 方式）
    // 如果视频需要更多延迟，音频需要等待
    uint32_t audio_sync_delay = 0;
    uint32_t video_sync_delay = 0;
    
    if (av_offset_ms > 0) {
        // 视频领先 → 音频需要延迟
        audio_sync_delay = av_offset_ms;
    } else if (av_offset_ms < 0) {
        // 音频领先 → 视频需要延迟
        video_sync_delay = -av_offset_ms;
    }
    
    // 3. 通过 SetMinimumDelay 传递 sync_delay
    audio_jitter_buffer.SetMinimumDelay(audio_sync_delay);
    video_jitter_buffer.SetMinimumDelay(video_sync_delay);
    
    // 4. target_delay 会自动变为 max(jitter_delay, sync_delay)
}
```

### 10.2 视频对比

| 特性 | WebRTC Video JitterBuffer | AdaptiveVideoJitterBuffer |

## 十一、设计结论

| 问题 | 结论 |
|------|------|
| **驱动方式** | mixlib 定时拉取，jitter buffer 被动响应 |
| **TryOutputFrames 返回 false** | 音频不返回 false（有 PLC），视频可返回 false |
| **变速实现** | jitter buffer 内部跳帧，mixlib 无感知 |
| **播放时钟** | 不需要，缓冲状态判断足够（录制场景） |
| **同步控制** | 通过 `SetMinimumDelay` 传入 sync_delay，`target_delay = max(jitter, sync)` |
| **PLC 实现** | **音频必须有 PLC（重复最后一帧），视频不做 PLC** |
| **时间判断** | 音视频都用缓冲状态判断（录制场景简化） |

## 十二、PLC 设计决策

### 12.1 音频 PLC

**必须实现**，原因：
- 音频播放不能中断，否则有爆音、空白感
- WebRTC NetEq 设计：必须返回数据

**实现方式**：
| 方案 | 复杂度 | 效果 | 选择 |
|------|--------|------|------|
| 静音填补 | 最简单 | 有明显空白感 | ❌ |
| **重复最后一帧** | 简单 | 比静音好，过渡平滑 | ✅ |
| 线性预测 | 中等 | 更平滑 | 可选（后续） |
| WSOLA | 复杂 | 最平滑 | 可选（后续） |

**具体实现**：
```cpp
bool AdaptiveAudioJitterBuffer::TryOutputFrames(std::vector<AudioFrame>& out_frames) {
    // 队列有数据 → 正常输出
    if (CanOutputFrame() && !packet_queue_.empty()) {
        // ... 正常解码输出
        // 缓存最后一帧用于 PLC
        last_audio_frame_ = decoded_frames.back();
        return true;
    }
    
    // 队列无数据但有缓存的最后一帧 → PLC（重复最后一帧）
    if (last_audio_frame_.IsValid()) {
        out_frames.push_back(last_audio_frame_);
        return true;  // 返回 true，有 PLC 数据
    }
    
    // 完全无数据 → 返回 false（极端情况）
    return false;
}
```

### 12.2 视频 PLC

**不做 PLC**，原因：
- 视频可以暂时无画面，用户感知不强
- WebRTC Video JitterBuffer 也不做 PLC
- 等待关键帧恢复是正确的策略

**实现方式**：
```cpp
bool AdaptiveVideoJitterBuffer::TryOutputFrames(std::vector<VideoFrame>& out_frames) {
    // 队列有数据且满足条件 → 输出
    if (CanOutputFrame()) {
        return AssembleAndOutput(out_frames);
    }
    
    // 无数据 → 返回 false，mixlib 处理（黑帧/等待）
    return false;
}
```

### 12.3 与 WebRTC 对比

| 类型 | WebRTC 实现 | AdaptiveJitterBuffer 实现 |
|------|-------------|--------------------------|
| **音频 PLC** | WSOLA（复杂） | 重复最后一帧（简单） |
| **视频 PLC** | 无 | 无 |
| **音频返回** | 必须返回数据 | 必须返回数据（有 PLC） |
| **视频返回** | 可返回 null | 可返回 false |
