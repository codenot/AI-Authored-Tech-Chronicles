# WebRTC Jitter Buffer 实现详解

## 一、核心延迟参数

### 1.1 NetEq 延迟类型

| 参数 | 定义 | 作用 |
|------|------|------|
| `target_delay` | NetEq 试图维持的延迟（packet 数） | 最终播放延迟目标 |
| `base_target_level` | 基于网络抖动计算的基准延迟 | 抖动缓冲核心 |
| `minimum_delay` | 用户设置的最小延迟下限 | 同步延迟通过此接口传入 |
| `maximum_delay` | 用户设置的最大延迟上限 | 延迟限制 |
| `preferred_delay` | 低延迟场景的目标 | 可选的低延迟目标 |
| `current_delay` | 当前实际缓冲延迟 | 实时状态 |

### 1.2 关键公式

**核心延迟计算公式**：
```
target_delay = max(
    base_target_level,           // 抖动延迟
    minimum_delay,               // 用户最小延迟（包含 sync_delay）
    preferred_delay              // 可选的低延迟目标
)

target_delay = min(target_delay, maximum_delay)  // 应用上限
```

**不是相加，而是取最大值！**

## 二、抖动延迟计算

### 2.1 base_target_level 计算方式

WebRTC NetEq 使用 `DelayManager` 计算基准延迟：

```cpp
// 基于包到达间隔统计
base_target_level = statistical_delay + safety_margin

// statistical_delay 来自：
// - 包到达间隔的最大值
// - 或基于历史统计的分位数
```

**关键点**：
- 使用 **packet inter-arrival time** 统计
- 不是简单的到达时间差
- 需要转换为 packet 数量

### 2.2 抖动统计方式

```cpp
// 记录每个包的到达间隔
inter_arrival_time = current_arrival - last_arrival

// 与理想间隔对比（基于 RTP timestamp）
ideal_interval = rtp_diff * 1000 / clock_rate

// 抖动值
jitter = inter_arrival_time - ideal_interval
```

## 三、音视频同步机制

### 3.1 StreamSynchronization 类

**位置**: `modules/video_coding/synchronization/stream_synchronization.cc`

**核心职责**：
- 计算音视频相对延迟偏差
- 决定同步调整策略

### 3.2 同步延迟传递方式

**关键实现**：

```cpp
// 音视频同步的核心：让音频和视频的实际播放时间对齐
// target_delay = max(jitter_delay, sync_delay)

// 音频侧通过 SetMinimumDelay 接收同步延迟
neteq_->SetMinimumDelay(ssrc, sync_delay_ms);
```

**sync_delay 计算**：

```cpp
// 音视频相对延迟偏差
av_offset = video_rtp_time - audio_rtp_time

// 根据偏差决定 sync_delay
if (av_offset > 0) {
    // 视频领先，音频需要延迟
    audio_sync_delay = av_offset
}
else if (av_offset < 0) {
    // 音频领先，视频需要延迟
    video_sync_delay = -av_offset
}
```

### 3.3 同步策略

| 场景 | 策略 | 实现 |
|------|------|------|
| 音频领先视频 | 音频增加延迟 | `SetMinimumDelay(audio_sync_delay)` |
| 视频领先音频 | 视频增加延迟 | 视频渲染时间延后 |
| 偏差较小 | 速率微调 | 加速/减速 |

## 四、播放时间判断

### 4.1 视频 JitterBuffer 播放判断

**WebRTC Video JitterBuffer 使用时间点判断**：

```cpp
// 计算帧的播放时间（不含 render_delay）
// render_delay 是已知的设备延迟补偿，不是额外加的延迟
render_time_ms = rtp_timestamp_to_ms(frame.rtp_ts) + target_delay

// 判断是否应该播放
if (current_time >= render_time_ms) {
    // 可以输出帧
    return frame;
} else {
    // 时间未到，等待
    return null;
}
```

**注意**：`render_delay` 在 WebRTC 中指的是：
- **音频设备延迟**（Audio Device Latency）：从数据送到音频设备到实际播放的时间（如 10-40ms）
- 这是**已知延迟的补偿值**，不是同步时额外引入的延迟
- 音频播放时间需要加上这个已知延迟来预测实际播放时刻

### 4.2 音频 NetEq 播放判断

**NetEq 使用缓冲深度判断**：

```cpp
// GetAudio() 每 10ms 被调用一次
bool GetAudio(AudioFrame* frame) {
    // 检查缓冲状态
    if (buffer_depth >= target_delay) {
        // 正常播放
        return NormalOperation(frame);
    } else if (buffer_depth < target_delay * 0.5) {
        // 缓冲不足，加速追赶（WSOLA）
        return Accelerate(frame);
    } else if (buffer_depth > target_delay * 2.0) {
        // 缓冲过多，减速或跳帧
        return Expand(frame);  // WSOLA 时间拉伸
    }
}
```

### 4.3 render_delay 的正确理解

```
render_delay ≠ 同步延迟

render_delay = 音频设备硬件延迟（已知值）
             = 从送入设备到实际播放的时间（如 10-40ms）

用途：
- 预测音频实际播放时间：audio_play_time = send_to_device_time + render_delay
- 用于时间对齐计算，不是额外引入的延迟
```

**同步延迟**：
- 通过 `SetMinimumDelay()` 传入
- 影响 `target_delay = max(jitter_delay, sync_delay)`
- 是真正为了音视频对齐而引入的缓冲延迟
```

## 五、变速播放实现

### 5.1 音频变速：WSOLA

**WebRTC NetEq 使用 WSOLA (Waveform Similarity Overlap-Add)**：

| 操作类型 | 说明 | 实现 |
|---------|------|------|
| `kNormal` | 正常播放 | 直接输出 |
| `kAccelerate` | 加速追赶 | WSOLA 压缩（去除相似段） |
| `kExpand` | 减速/PLC | WSOLA 拉伸（复制相似段） |
| `kCodecPLC` | 编解码器 PLC | 使用编解码器内置 PLC |

### 5.2 视频变速：跳帧

**WebRTC Video JitterBuffer 不使用时间拉伸**：

| 操作 | 说明 |
|------|------|
| 加速 | 跳过非关键帧 |
| 减速 | 正常输出（播放端自然减速） |
| PLC | 无（等待关键帧） |

## 七、时间戳处理

### 7.1 RTP 时间戳回绕

**WebRTC 使用 TimestampUnwrapper**：

```cpp
class TimestampUnwrapper {
    int64_t unwrapped_ts_;
    uint32_t last_ts_;
    
    int64_t Unwrap(uint32_t ts) {
        int32_t diff = ts - last_ts_;
        if (diff > 0x80000000) {
            // 正向回绕
            unwrapped_ts_ -= 0x100000000LL;
        } else if (diff < -0x80000000) {
            // 负向回绕
            unwrapped_ts_ += 0x100000000LL;
        }
        unwrapped_ts_ += diff;
        last_ts_ = ts;
        return unwrapped_ts_;
    }
};
```

### 7.2 RTP-NTP 时间映射

**从 RTCP Sender Report 获取**：

```cpp
// RTCP SR 包含：
// - ntp_timestamp (64-bit NTP 时间)
// - rtp_timestamp (32-bit RTP 时间)

// 时间转换公式
local_time_ms = ntp_time_ms + (rtp_ts - base_rtp_ts) * 1000 / clock_rate
```

## 八、buffer_depth 计算

### 8.1 正确计算方式

**使用 RTP timestamp 差值**：

```cpp
uint32_t CalculateBufferDepth() {
    if (packet_queue_.empty()) return 0;
    
    uint32_t oldest_rtp = oldest_packet->GetTimestamp();
    uint32_t newest_rtp = newest_packet->GetTimestamp();
    
    // 处理回绕
    int64_t rtp_diff = newest_rtp - oldest_rtp;
    if (rtp_diff < 0) rtp_diff += 0x100000000LL;
    
    // 转换为毫秒
    return rtp_diff * 1000 / clock_rate;
}
```

### 8.2 为什么不用到达时间差

```
错误方式：buffer_depth = newest_arrival - oldest_arrival

问题：
- 网络波动导致连续包时间差很大
- 不能反映实际缓冲的数据量
- 只反映网络传输时间

正确方式：buffer_depth = (newest_rtp - oldest_rtp) / clock_rate

优点：
- 反映队列中实际缓存了多少数据时长
- 不受网络延迟波动影响
- 准确反映播放端需要处理的数据量
```

## 九、关键设计决策

### 9.1 驱动模式

| 类型 | 驱动方 | 返回方式 |
|------|-------|---------|
| **音频 NetEq** | Audio Device Module 定时拉取（10ms） | 必须返回数据（PLC） |
| **视频 JitterBuffer** | 渲染定时器或帧可用事件 | 可返回 null（等待） |

### 9.2 PLC 处理

| 类型 | PLC 方式 | 原因 |
|------|---------|------|
| **音频** | 必须生成填补数据 | 播放不能中断，否则有爆音 |
| **视频** | 无 PLC，等待关键帧 | 视频可以暂时无画面 |

### 9.3 同步延迟传递

```
sync_delay → SetMinimumDelay() → target_delay = max(jitter, sync_delay)

关键点：
- sync_delay 作为 minimum_delay 传入
- target_delay 取最大值，保证两者都满足
- 不是 jitter_delay + sync_delay 相加
```

## 十一、移植建议

### 11.1 必须修改

1. **延迟计算改为取 max**
   ```cpp
   target_delay = std::max(jitter_delay, sync_delay);
   ```

2. **添加 SetMinimumDelay 接口**
   ```cpp
   void SetMinimumDelay(uint32_t delay_ms);
   ```

### 11.2 可选优化

1. **视频播放判断**：可继续用缓冲状态判断（录制场景够用）
2. **音频变速**：可继续用简单跳帧（或后续集成 WSOLA）
3. **播放时钟**：录制场景可能不需要精确时间点判断
